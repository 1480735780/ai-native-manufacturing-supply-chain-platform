# ADR-018 巡检规则配置（版本化 YAML + 入队快照）

- 状态：已接受（2026-11-25，F-015 阶段 4）
- 关联：ADR-014 配置管理、ADR-007 认证授权、ADR-011 状态存储、ADR-015 API 契约
- 代码位置：`zero-one-10wms/wms-agent/config/scan.yaml`、`zero-one-10wms/wms-agent/app/scan/config.py`

## 1. 背景

异常巡检（F-015）有四类规则（到期 `EXP-*`、待上架超时 `NOUP-OVERDUE`、收货延迟 `DELAY-OVERDUE`、积压增长 `BACKLOG-GROWTH`），每类都有阈值、责任岗位、通知接收人和调度参数。

这些参数此前散落在两处：

1. Python 代码里的 `DEFAULT_CONFIG` 常量；
2. 环境变量（`WMS_AGENT_SCAN_WAREHOUSES`、`WMS_AGENT_NOTIFICATION_MODE`、`WMS_AGENT_ALERT_RECIPIENTS`）。

带来三个具体问题：

- **改阈值要改代码**：运维想调 `noUp.p0Hours` 必须发版；
- **历史不可回放**：一条告警是按哪套阈值判出来的，事后无法证明。异步队列下这个问题更严重——任务入队到执行之间可能隔几分钟，期间阈值被改了，执行结果与入队意图不一致；
- **配置漂移不可检测**：两套来源（常量 + env）谁生效说不清。

## 2. 决策

**巡检非密规则使用仓库内版本化 YAML（`wms-agent/config/scan.yaml`），启动时一次性加载并校验，入队时冻结为 canonical JSON 快照，worker 只按快照执行。**

四条不可让步的性质：

| 性质 | 实现 |
|---|---|
| 启动即校验，非法拒绝启动 | `load_scan_config()` 抛 `ScanConfigError`，`create_app()` 不吞异常 |
| 不热重载 | 进程生命周期内只加载一次，存 `app.state.scan_config`；改文件需重启 |
| 入队冻结 | `POST /agent/scan` 把 `configSnapshot` / `configHash` / `configVersion` 写进 `agent_scan_runs` |
| 执行只读快照 | worker 从 `run["configSnapshot"]` 反序列化，**永不回退读当前 YAML** |

### 2.1 配置结构

```yaml
version: "v0.2.0"          # 配置版本，进快照
warehouses: ["W01"]        # 仓库范围，首版强制单仓
scan:                      # 取数与预算
  pageSize: 100
  maxPages: 20
  requestTimeoutSeconds: 3
  sourceBudgetSeconds: 30
  scanBudgetSeconds: 120
  concurrency: 1
rules:                     # 四类规则阈值
  expiry: {expiredDays: 0, nearDays: 7, nearRatio: 0.3333, watchDays: 30}
  noUp:   {p0Hours: 8, p1Hours: 4, p2Hours: 2}
  delay:  {p0Hours: 24, p1Hours: 2, p2Hours: 0}
  backlog: {growthRatio: 0.30, absoluteDelta: 10, baselineScans: 3, consecutiveForP1: 3}
routing:                   # 责任路由：rule_id + warehouse → 岗位 + 接收人
  - {rule_id: "EXP-*", warehouse: "W01", assignee_role: "qc_lead", recipients: ["admin"]}
notifications:             # 通知模式与默认接收人
  mode: "dry_run"
  recipients: ["admin"]
schedule:                  # 阶段 5 使用，当前默认关闭
  enabled: false
  cron: "*/15 7-23 * * *"
  timezone: "Asia/Shanghai"
```

### 2.2 启动校验清单

`app/scan/config.py` 用 pydantic（`extra="forbid"`）+ 自定义 YAML loader 拒绝以下情况，全部抛 `ScanConfigError`，**不允许静默降级到默认值**：

- 重复 key（`YAML 重复键: <key>（行 N）`）——PyYAML 默认静默取最后一个，会造成"改了没生效"的错觉；
- 非字符串 key；
- 非法类型 / 未知字段（`extra="forbid"`）；
- 阈值顺序违反 `p0Hours > p1Hours > p2Hours`、`watchDays >= nearDays`、`scanBudgetSeconds >= sourceBudgetSeconds`；
- 通知模式不在 `dry_run | in_app | full`；
- 路由 `rule_id` 未匹配任何已知规则（允许 `*` 通配）；
- 路由 `warehouse` 不在 `warehouses` 内；
- 仓库列表为空或重复；首版多于一个仓库由 `ensure_single_scan_warehouse()` 拒绝；
- 文件不可读、YAML 语法错误、顶层不是对象；
- 未知的 env 覆盖项。

### 2.3 canonical JSON 与哈希

```python
canonical_json(v) = json.dumps(v, ensure_ascii=False, sort_keys=True, separators=(",", ":"))
hash_config(v)    = "sha256:" + sha256(canonical_json(v).encode("utf-8")).hexdigest()
```

哈希覆盖**全部生效配置**（阈值、路由、通知模式与接收人、调度、仓库、版本）。

**关键实现约束（曾出过缺陷）**：哈希必须对 `json.loads(snapshot)` 得到的**原始 dict** 计算，不能对 `document.model_dump()` 计算。原因是 pydantic 会把 `p0Hours: 24` 归一化成 `24.0`，入队侧与消费侧算出不同的哈希，合法快照被判成篡改。该回归由 `tests/test_scan_config.py::test_snapshot_roundtrip_keeps_hash` 守住。

### 2.4 环境变量覆盖

允许的部署差异只有两项，且**覆盖后的最终生效配置**才进快照和哈希：

| env | 覆盖目标 |
|---|---|
| `WMS_AGENT_SCAN_WAREHOUSES` | `warehouses` |
| `WMS_AGENT_NOTIFICATION_MODE` | `notifications.mode` |
| `WMS_AGENT_ALERT_RECIPIENTS` | `notifications.recipients` |

实现方式：`create_app()` 检查 `settings.model_fields_set`，只有**显式设置过**的字段才作为 override 传入（未设置则用 YAML 值），覆盖后回写 `settings` 并生成快照。这样"YAML 说 dry_run、env 说 in_app"时，快照里记的是 `in_app`——即实际执行的那一套。

### 2.5 快照冻结与回放

| 阶段 | 行为 |
|---|---|
| 入队（`POST /agent/scan`） | 写 `configSnapshot`（canonical JSON 字符串）、`configHash`、`configVersion`、`notificationMode`（取自快照） |
| 迁移 | `V007__scan_config_snapshot.up.sql` 给 `agent_scan_runs` 加 `config_snapshot TEXT` / `config_version TEXT`；`config_hash` 沿用既有列 |
| 执行（worker） | 鉴权通过后取 `run["configSnapshot"]`；缺失 → `failed(config_snapshot_missing)`；`load_config_snapshot()` 校验哈希与版本；不符 → `failed(config_snapshot_hash_mismatch)` / `failed(config_snapshot_version_mismatch)` |
| 历史记录 | 阶段 4 之前的终态记录允许 `config_snapshot` 为空（不追溯补齐）；但在途 `queued/running` 缺快照**必须失败退出**，不得静默使用当前 YAML |

**检查顺序是有意的**：快照检查排在鉴权之后。鉴权失败是更早、更根本的失败语义（`auth_failed:*`），缺快照属于配置完整性失败。顺序颠倒会让安全类断言失效。

### 2.6 责任路由与通知接收人

三个字段语义严格区分，不互相顶替：

| 字段 | 语义 | 谁能写 |
|---|---|---|
| `routed_to` | **责任岗位**（如 `putaway_lead`），来自 YAML 路由 | 规则命中时由配置解析 |
| `assignee` | **实际认领人**（登录用户名） | 只有 `POST /alerts/{id}/claim` |
| `agent_notifications.recipient` | 通知接收人 | 见下方解析顺序 |

接收人解析（`resolve_route_targets()`）：

- **手动扫描**（`actor_type == "user"`）：默认只通知发起人，不因路由而扩散；
- **定时/服务扫描**：`notifications.recipients` 与路由命中的 `recipients` 合并去重；
- **解析不到任何接收人**：`counts.notificationsUnrouted += 1`，**不写占位账号**（写 `admin` 之类的兜底会让"没人负责"变成"看起来有人负责"）。

路由匹配用 `fnmatch(rule_id, pattern)` + `warehouse` 相等，支持 `EXP-*` 这类前缀。

## 3. 与 ADR-014 的关系（有意例外）

ADR-014 的决策是"非密配置进 Nacos，密钥走 env/`.env`"。本 ADR **有意例外**：巡检规则走仓库内版本化 YAML，不进 Nacos。

例外理由：

1. **必须可版本化、可 diff、可回放**。Nacos 的配置历史不提供与代码版本绑定的稳定标识，无法回答"这条告警是按哪一版规则判出来的"。YAML 在 git 里，`configVersion` 与 commit 天然对齐。
2. **必须能在离线/单机复现**。巡检是运维兜底能力，不能依赖配置中心可用性；本地 `git clone` + `uv sync` 就能跑出同样结果。
3. **变更必须走 code review**。阈值放宽会直接减少告警，属于需要评审的变更；Nacos 控制台改值绕过评审。
4. **配置结构复杂**。嵌套路由表用 YAML 表达 + pydantic 校验，比 Nacos 的扁平 key-value 更可控。

**例外边界（不可越界）**：

- 只有**巡检规则**这一类配置适用本例外；网关地址、模型名、超时等仍按 ADR-014 走 Nacos。
- **密钥一律不进 YAML**：service API Key、DB URL、JWT 公钥路径、LLM Key 仍只走环境变量或本地 `.env`。快照里不含任何密钥字段，由 `test_snapshot_contains_no_secrets` 守住。
- 若未来需要集中下发多仓配置，应先修订 ADR-014，而不是继续扩大本例外。

## 4. 规则版本 vs 配置版本

两个版本号是**正交**的，回答不同问题：

| | 规则版本 | 配置版本 |
|---|---|---|
| 字段 | `rule_version`（如 `no_up=v0.2.0`） | `config_version`（如 `v0.2.0`） |
| 归属 | 规则**代码**的语义版本 | 配置**文档**的版本 |
| 变更触发 | 判定逻辑改变（如指纹算法、object_id 组成） | 阈值/路由/通知/调度参数改变 |
| 用途 | 判断告警是否可与历史比较；改版本即重置基线 | 判断配置是否漂移；参与 `config_hash` |
| 进哈希 | 否 | 是（`version` 字段在快照内） |

举例：把 `noUp.p0Hours` 从 8 改成 6，`config_version` 与 `config_hash` 变，`rule_version` 不变——判定逻辑没变，只是参数变了。反过来，把 `BACKLOG-GROWTH` 的基线算法从"前 3 次"改成"前 5 次"，`rule_version` 必须变（旧基线不可比），`config_hash` 也可能因新增参数而变。

## 5. 后果

**收益**：

- 调阈值不用发版，改 YAML + 重启即可；
- 每条扫描记录可证明"按哪一版配置、哪一版规则"执行，支持事后回放与审计；
- 在途任务不受配置变更影响——入队即冻结；
- 配置错误在启动时暴露，不会跑到一半才发现阈值反序。

**代价**：

- 改配置需要重启进程（无热重载）——有意取舍，热重载会让"当前生效配置"变得不可判定；
- 多实例部署时必须保证各实例 `scan.yaml` 一致，否则同一条队列任务在不同 worker 上会因哈希校验失败而失败退出。这是**正确的失败**：说明部署不一致，应修复部署而不是放宽校验；
- `config_snapshot` 会让 `agent_scan_runs` 单行增大约 1–2 KB。按当前扫描频率（15 分钟级）可接受。

## 7. 未覆盖范围（保留至后续阶段）

- **调度器未启用**：`schedule.enabled` 默认 `false`，阶段 5 才实现自动 resolved 与内部定时调度；本 ADR 只冻结调度**配置**，不实现调度**行为**。
- **多仓未开放**：`ensure_single_scan_warehouse()` 仍强制单仓，多仓路由已能表达但会被启动校验拒绝。
- **热重载不做**：明确不做，需要变更即重启。
