## 1. 背景

阶段 0 曾记录一条「安全未闭环项」：网关对巡检端点不要求登录，无 token 的请求能穿过网关到达 agent，由 agent 自己拒绝。当时按 ADR-007 处理为「agent 侧自验」并保留备注。阶段 7 要求给出明确结论。

## 2. 实测结论（2026-11-25，运行中的网关 10001，修复前）

网关的认证与鉴权逻辑不在仓库源码里，而在第三方 starter `zero-one-cloud-starter-gateway`；仓库侧只有 `LoadResourcesDataImpl`（从 Redis `AUTH:RESOURCE_ROLES` 取路径对应角色）。静态反汇编与实测一致，结论如下。

| 现象 | 实测 | 含义 |
|---|---|---|
| 无 token，任意方法、任意路径 | 网关直接转发到下游（`/agent/scan/retention/run` 的 POST 也到达 agent） | 网关对匿名请求不做认证 |
| 无 token 访问业务接口 | `GET /dashboard/query-pend-snapshot`、`GET /daycheck/no-up/get-no-up-goods-page` 返回 `code=10000` 与业务数据 | 不止巡检端点；**下游不自验的接口对匿名开放** |
| 带错误角色的 token 访问已登记资源 | 财务角色 cw 访问登记为 `insp_read` 的 `/dashboard/query-pend-snapshot` → `code=10000` 与数据 | 资源角色（`AUTH:RESOURCE_ROLES`）在当前运行配置下**没有被强制执行** |
| 带无法解析的 token | 网关返回 `{"code":401,"message":"暂未登录或TOKEN已经过期"}`（HTTP 200 外壳） | 网关唯一生效的校验：token 存在时必须能解析为 JWT，且未登出 |
| `/agent/**` 无 token | 穿过网关后由 agent 返回 HTTP 401 `{"code":401,"message":"缺少 Bearer token"}` | 巡检端点的认证与授权**完全由 agent 自己保证** |

也就是说，阶段 0 的表述「网关 GET 无 token 放行」偏窄：实际是**无 token 全放行 + 资源角色不生效**，范围是整个 WMS API，而不是巡检端点独有的问题。

## 3. 根因（2026-11-26 反编译 starter 后已完全定位）

starter jar：`com.zeroone.star:zero-one-cloud-starter-gateway:1.0.0-SNAPSHOT`（22 750 字节，16 个类，`javap -p -c` 反编译）。

1. **匿名放行**：`filter.AuthGlobalFilter.filter` 取到 token 后第一句就是 `if (StringUtils.isEmpty(token)) return chain.filter(exchange);` —— 没有 `Authorization` 头时直接转发下游，没有任何 401。
2. **资源角色不生效**：`authorization.AuthorizationManager.check` 第一句是 `if (!properties.isOpenAuthorization()) return new AuthorizationDecision(true);`。仓库 `wms-gateway/src/main/resources/application.yaml` 写的是 `open-authorization: true`，但 **Nacos `system.yaml`（dev 命名空间 `4833404f-4b82-462e-889a-3c508160c6b4`）把它覆盖成 `false`**，所以运行期授权一律放行，`AUTH:RESOURCE_ROLES` 根本不参与判定。
3. 叠加项：`ResourceServerConfig.springSecurityFilterChain` 把 `inner-paths` 配成 `permitAll`（不是“需凭证”），而 `LoadResourcesDataImpl.loadRolesByUrlPath` 对未登记路径返回 `null`。

## 4. 影响范围

- **巡检 agent（`/agent/**`）**：不受此缺口影响。agent 用本地公钥验 RS256 签名与 `exp`，逐端点做角色与仓库范围校验；服务令牌另做 `token_use` / 角色 / 账号 / 仓库强校验。网关是否认证，不改变 agent 的判定。
- **其余 Java 服务**：依赖网关做认证与资源角色鉴权。修复前匿名与越权请求都能拿到数据。这是平台级缺口，已由本次修复覆盖（见第 5、6 节）。

## 5. 修复实现（仓库侧，2026-11-26）

不改第三方 starter（避免影响全部模块的隐式行为），改在 `wms-gateway` 自有代码：

- `security/GatewayAccessProperties.java`：`@ConfigurationProperties(prefix = "zo.cloud.starter.gateway")`，复用 starter 同前缀的 `white-paths` / `inner-paths`，并新增：
  - `authority-claim-name`（默认 `authorities`，与实际签发的服务令牌 claim 一致；starter 默认 `SCOPE_`/`scope` 取不到角色）
  - `authority-prefix`（默认空）
  - `deny-unregistered`（默认 `false`，见第 7 节未决）
- `security/GatewayAccessFilter.java`：`implements WebFilter, @Order(Ordered.HIGHEST_PRECEDENCE)`。
  - **为什么是 `WebFilter` 而不是 `GlobalFilter`**：Spring Security 的 `WebFilterChainProxy` 排在网关 `GlobalFilter` 链之前，用 `GlobalFilter` 时非法令牌会先被 starter 的 `RestfulAuthenticationEntryPoint` 处理成 `HTTP 200 + code=401`，拿不到真实 401/403。
  - 判定顺序：OPTIONS 与 `white-paths`（`AntPathMatcher`）→ 放行；缺 `Authorization: Bearer` → **401**；`ReactiveJwtDecoder.decode` 失败（含同步抛出的 `BadJwtException`）→ **401**；`TokenExtendsValidate.isLogout(token)`（传裸 token）→ **401「用户凭证已注销」**；命中 `inner-paths` → 只验凭证不验角色；其余路径 → 读 `AUTH:RESOURCE_ROLES`（未登记则按 `父路径/**` 逐级回退 ≤8 层）→ 角色不匹配 → **403**。
  - 响应为真实 HTTP 状态码 + `application/json;charset=UTF-8`：`{"code":401|403,"message":"..."}`。
- 回归：`GatewayAccessFilterTest` 15 例（白名单、OPTIONS、无 token、非 Bearer、验签失败、同步解码异常、已注销、正确角色、错误角色、未登记开关两种取值、inner 路径、父路径回退、前缀剥离、响应体编码），已加入 `init.sh` 的 `test_filter` 与 surefire 报告清单（模块列表新增 `wms-gateway`）。

## 7. 未决与残余风险

1. **`deny-unregistered` 仍为 `false`，dev 改为审计模式**：未登记/角色不匹配记录 `AUTHZ_AUDIT` 后放行，不再走旧的未登记前缀清单硬拦截。实测覆盖率：`t_s_function` 的 `functiontype` 分布 `{1: 8, 0: 96, null: 29}`；前端 `src/apis` 535 个路径中已登记带角色 5、未登记 518、白名单/内部 12（0.93%）。接口冻结后再按分组草案落库、观察联调流量、收敛误报并切 `deny-unregistered=true`。
2. **`/login/logout` 对 service-token 返回 `code=9999` 已修复**：logout 加入服务令牌路径白名单，login 侧删除当前 access token 即视为成功，不再要求不存在的 refreshToken。真实探针 logout=10000、同令牌随后 HTTP 401。
3. **巡检菜单/路由浏览器回归已完成**：生产构建 + 本地 preview + 无头 Chrome 验证 ckjl/admin 正常路径与 `/Inspection/Alerts` 大小写变体放行，cw 两种路径均跳 `/forbidden`；mock `current-user=null` 与 `get-menus=[]` 均失败关闭。修复路径大小写、空用户、旧菜单清理与 main.ts HTTP/路由安装顺序，前端 15 例通过。证据 `.runtime_tmp/r7_route_guard_result.json`。`/sysmanager/**` 等非巡检存量菜单仍未逐一回归。
4. **Nacos `system.yaml` 的 `open-authorization` 仍是 `false`**：本次修复不依赖该开关（自研过滤器独立判定），但若日后有人改回 `true`，starter 的 `AuthorizationManager` 会与自研过滤器叠加（两层判定，行为仍为更严格者，不会放宽）。
5. **网关无 websocket 路由**：`application.yaml` 只有 HTTP 路由（`ws` 服务 10230 未配置路由），因此「浏览器无法为 WS 握手设置 Authorization 头」的兼容性问题当前不存在；若后续新增 WS 路由，需要为握手补 query `token` 兼容。
6. **服务令牌边界依赖 `token_use` 声明 + 取数端点清单**：过滤器按 `claims.token_use == "agent_service"` 识别服务令牌，并只放行 `service-token-paths`。`wms-login` 签发的令牌已带该声明（实测 `/agent/scan/metrics` 200、`/md/goods/query` 403）；若更换签发实现，必须同步该声明，否则服务令牌会被当作普通用户令牌处理。
   - **2026-11-26 第六轮复核后新增约束**：巡检 Agent 是**用服务令牌经网关读业务数据**的，因此 `service-token-paths` 必须与六类巡检数据源端点保持同步（`/daycheck/no-up/get-no-up-goods-page`、`/daycheck/yi-chang/get-yichang-down-page`、`/daycheck/delay/im-delay`、`/stock/expiry-warning/query-all`、`/daycheck/temperature/query`、`/dashboard/query-pend-snapshot`，另含 `/agent/**`）。第二轮加固时只写了 `/agent/**`，导致六源全部 403、扫描被标 partial（`sourceStatus.status=error, errorSummary=http_403`），修复后六源实测 200、六源扫描 `partial=false`。**新增巡检数据源时必须同步该清单**，`GatewayAccessFilterTest` 已加两例（取数端点放行、未声明端点 403）锁死这条边界。
7. **`issuer` 已对服务令牌配置并实测**：`AgentTokenSigner` 写入 `iss=wms-login-agent`，网关对 `token_use=agent_service` 强制比对；存量用户令牌没有 iss，因此不全局强制，避免打断登录。真实探针确认签发、数据源访问、logout 与注销后 401 全通过。
