# ADR-021 网关认证与鉴权缺口（生产上线阻塞）

- 状态：已接受（2026-11-25，F-015 阶段 7「生产安全门」）；结论是**阻塞上线**，不是已修复
- 关联：ADR-007 认证授权（管理员接口）、ADR-015 API 契约、ADR-020 巡检数据保留与归档
- 代码位置：巡检侧护栏 `zero-one-10wms/wms-agent/app/security.py`（`require_principal`、各 `can_*`）、回归 `wms-agent/tests/test_scan_stage7.py` 第 6 段（路由逐条扫描）
- 依据：用户 2026-11-25 阶段 7 范围「“网关 GET 无 token 放行”必须修复或明确阻塞上线，不能继续只作为备注」；对运行中网关（10001）的实测证据见第 2 节

## 1. 背景

阶段 0 曾记录一条「安全未闭环项」：网关对巡检端点不要求登录，无 token 的请求能穿过网关到达 agent，由 agent 自己拒绝。当时按 ADR-007 处理为「agent 侧自验」并保留备注。阶段 7 要求给出明确结论。

## 2. 实测结论（2026-11-25，运行中的网关 10001）

网关的认证与鉴权逻辑不在仓库源码里，而在第三方 starter `zero-one-cloud-starter-gateway`；仓库侧只有 `LoadResourcesDataImpl`（从 Redis `AUTH:RESOURCE_ROLES` 取路径对应角色）。静态反汇编与实测一致，结论如下。

| 现象 | 实测 | 含义 |
|---|---|---|
| 无 token，任意方法、任意路径 | 网关直接转发到下游（`/agent/scan/retention/run` 的 POST 也到达 agent） | 网关对匿名请求不做认证 |
| 无 token 访问业务接口 | `GET /dashboard/query-pend-snapshot`、`GET /daycheck/no-up/get-no-up-goods-page` 返回 `code=10000` 与业务数据 | 不止巡检端点；**下游不自验的接口对匿名开放** |
| 带错误角色的 token 访问已登记资源 | 财务角色 cw 访问登记为 `insp_read` 的 `/dashboard/query-pend-snapshot` → `code=10000` 与数据 | 资源角色（`AUTH:RESOURCE_ROLES`）在当前运行配置下**没有被强制执行** |
| 带无法解析的 token | 网关返回 `{"code":401,"message":"暂未登录或TOKEN已经过期"}`（HTTP 200 外壳） | 网关唯一生效的校验：token 存在时必须能解析为 JWT，且未登出 |
| `/agent/**` 无 token | 穿过网关后由 agent 返回 HTTP 401 `{"code":401,"message":"缺少 Bearer token"}` | 巡检端点的认证与授权**完全由 agent 自己保证** |

也就是说，阶段 0 的表述「网关 GET 无 token 放行」偏窄：实际是**无 token 全放行 + 资源角色不生效**，范围是整个 WMS API，而不是巡检端点独有的问题。

根因线索（未完全定位，修复前须确认）：`application.yaml` 的 `open-authorization: true` 生效，starter 的 `AuthorizationManager` 对无匹配角色默认拒绝；但 `LoadResourcesDataImpl.loadRolesByUrlPath` 对未登记路径返回 `null`，且 inner-paths 在安全链里被 `permitAll()`。两者叠加后的实际行为以第 2 节实测为准。

## 3. 影响范围

- **巡检 agent（`/agent/**`）**：不受此缺口影响。agent 用本地公钥验 RS256 签名与 `exp`，逐端点做角色与仓库范围校验；服务令牌另做 `token_use` / 角色 / 账号 / 仓库强校验。网关是否认证，不改变 agent 的判定。
- **其余 Java 服务**：依赖网关做认证与资源角色鉴权。当前运行配置下，匿名与越权请求都能拿到数据。这是平台级缺口，超出本任务（异常巡检 agent）的改动范围。

## 4. 决策

1. **登记为生产上线阻塞项**：在网关补齐「非白名单路径必须携带有效 Bearer token」与「按 `AUTH:RESOURCE_ROLES` 做角色校验」并通过回归之前，v0.2.0 不得在生产环境上线。该项写入 `PROGRESS.md` 的 blocker 与 `feature_list.json` F-015 evidence，不再只是备注。
2. **巡检端点以 agent 自验为准**，并把它固化成回归：`tests/test_scan_stage7.py` 第 6 段遍历巡检路由表，对每条路由、每种方法，用「无 token / 无法解析的 token / 用别的私钥签的 token / 过期 token / `alg=none`」五种凭据调用，全部必须返回 HTTP 401；并断言路由表覆盖全部已知端点，新增端点漏挂 `require_principal` 会直接失败。对照组用测试公钥签出的管理员令牌放行，证明 401 来自凭据校验。
3. **不在本任务里修改网关**。原因：缺口在第三方 starter 的链路与仓库配置的组合上，影响全部模块；在未摸清登录、验证码、文件预览、WebSocket 握手等匿名路径之前加「一刀切」过滤器，风险是让正常流程 401。修复应由平台侧按第 5 节方案单独立项、全模块回归。

## 5. 修复方案（平台侧待办）

- 认证：在 `wms-gateway` 增加仓库自有的 `WebFilter`，对非 `white-paths` 的请求要求 `Authorization: Bearer` 且能通过 JWT 解码与登出校验，否则 401；白名单逐条确认后再保留。
- 鉴权：先确认 starter `AuthorizationManager` 的真实判定路径（可用单测或调试版 jar），再选择「修正 `LoadResourcesDataImpl` 的未登记路径返回值」或「自有 `SecurityWebFilterChain` 按 `AUTH:RESOURCE_ROLES` 判定」；未登记路径默认拒绝。
- 回归：为网关补一组契约测试（匿名 401、错角色 403、未登记路径 403、白名单 200、登出 token 401），并纳入 `init.sh --java-test`。

## 6. 验证证据

- 实测脚本输出：`zero-one-10wms/.runtime_tmp/_probe_gateway_75_out.json`、`_probe_gateway_75b_out.json`（只读探测，未改任何数据）。
- 护栏回归：`tests/test_scan_stage7.py` 第 6 段 3 例通过（15 条路由 × 5 种凭据全部 401；对照组放行）。
