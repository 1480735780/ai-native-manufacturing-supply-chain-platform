# 预警管理模块 · 异常巡检 Agent 需求背景与设计动因

> 文档定位：WMS Agent 产品线 v0.2 的需求背景与设计动因，服务于「预警管理 + 每日检查 + 系统首页 + 通知提醒/消息服务」构成的异常巡检闭环。

---

## 一、具体业务场景

### 1.1 场景定义

异常巡检 Agent 面向的是仓储日常运营中的**「异常发现与前置处置」场景**：在仓库作业持续运行的过程中，系统主动、周期性地检查那些「已经发生但尚未被处理」和「即将发生但尚可干预」的业务异常，把结果整理成**带证据链、带分级、带责任人、带建议动作**的告警清单，推送到对应岗位，并跟踪到关闭。

它关注的异常不是系统故障，而是**业务状态偏离**，具体覆盖六类对象：

| 异常对象 | 业务含义 | 现状数据入口 |
|---|---|---|
| 效期异常 | 已过期、临期（剩余天数低于阈值） | 预警管理 / 效期预警 |
| 收货未上架 | 已验收但超过时限仍未上架，占用月台与库容 | 每日检查 / 收货未上架 |
| 进货延时 | 通知单约定到货时间已过但货未到 | 每日检查 / 进货延时示警 |
| 出货异常 | 出库过程中出现的异常明细 | 每日检查 / 出货异常 |
| 温度异常 | 库房或商品温度超出其温度属性允许区间 | 每日检查 / 温度维护（只读侧） |
| 待办积压 | 待收货、待上架、待拣货任务量超过承载 | 系统首页 / 货物待办统计 |

### 1.2 参与角色与使用时刻

| 角色 | 关注异常 | 使用时刻 |
|---|---|---|
| 值班主管 | 全局分级清单、超时未处理项 | 班前 30 分钟、班中定时、交接班 |
| 收货组 / 上架组 | 收货未上架、进货延时 | 每批收货完成后、班中 |
| 质检 / 效期专员 | 已过期、临期批次 | 每日固定时段 |
| 客服 / 单证 | 出货异常、异常出库通知 | 出库任务确认后 |
| 仓库经理 | 趋势、重复发生项、处理时效 | 每日复盘、周会 |

### 1.3 一个典型运行日（现状 vs 目标）

**现状**：早班主管提前到岗，依次打开「每日检查」下的收货未上架、出货异常、温度维护、进货延时示警四个页面，再打开「预警管理 / 效期预警」，逐页设置条件、翻页、点「导出数据」生成 Excel，人工比对后在企业微信群里逐条 @ 责任人。夜班与周末时段无人主动查看，异常持续累积到下一个工作日。

**目标**：巡检按班次自动执行，主管到岗时看到的是一张**按紧急度排序、已去重、已归属责任人**的清单；每条告警可展开查看来源单据、关键字段、命中规则与 traceId；责任人认领后状态流转，超时未认领自动升级；全程只读，处置动作仍由人在原有业务页面完成。

## 二、系统架构与业务运行背景

### 2.1 Agent 在系统中的位置

系统为三栈架构：Vue3 前端经 `wms-gateway` 统一进入，Java 承担业务事务与规则校验，C++ 承担储位、库内、盘点、计费与预警等能力，共享 MySQL / Redis / Nacos 等中间件。

异常巡检 Agent 是独立的 Python 微服务（`wms-agent`），**不直读业务库**，所有业务数据经网关调用现有 REST 接口获取，并透传真实用户 JWT，权限沿用现有 RBAC；自身只在独立 schema 中保存会话、trace 与告警状态。架构文档中已预留 `POST /agent/scan` 作为巡检入口，v0.2 即填充该位置。

### 2.2 现有能力的分布（决定 Agent 能做什么）

| 现有模块 | 功能点 | 对 Agent 的意义 |
|---|---|---|
| 预警管理 | **仅 1 项**：获取预警列表（条件+分页） | 只有「查」，没有告警生命周期 |
| 每日检查 | 12 项，其中 8 项为只读检查、4 项为温度维护写入 | 巡检的主要数据源 |
| 系统首页 | 6 项待办与趋势统计 | 告警的证据与上下文 |
| 通知提醒 / 消息服务 | 7 + 3 项，含公告通知、消息通知、短信、邮件 | 巡检的推送通道 |
| 公用接口服务 | 24 项名称列表 | 把「客户说的名字」解析成业务 ID 的基础 |

### 2.3 业务运行逻辑与约束

- 业务链路为「通知单 → 收货 → 验收 → 上架 → 库存 → 出库 → 复核 → 回单」，异常天然分散在环节之间，而首版 Agent 不接入消息总线，因此巡检采用**定时拉取 + 规则判定**，不依赖事件推送。
- 库存、储位、效期视图口径分散在 Java 与 C++ 两侧，部分预警接口未纳入网关路由，Agent 只能使用已验证可达的接口。
- 按既定安全策略，写操作（改储位、上架、过账）不在 v0.2 范围内；巡检只读，唯一写动作是发送通知。

## 三、当前痛点与待解决问题

### 3.1 异常发现：被动、分散、无状态

1. **只有「查」没有「巡」**：预警管理只有一个查询列表接口，系统不具备主动扫描、主动通知的能力，异常是否被发现完全取决于人是否打开页面。
2. **入口分散、口径不一**：六类异常分布在预警管理、每日检查的四个子模块、系统首页与库存查询中，条件、分页、字段各不相同，无法形成一张全局清单。
3. **依赖导出与人工比对**：每日检查中有 3 个「导出数据」功能点，说明现行业务动作是「导出 Excel → 人工筛选」，时效以小时甚至天计。
4. **无分级、无去重、无生命周期**：列表按分页返回，没有 P0/P1/P2，没有「已知 / 处理中 / 已关闭 / 已忽略」状态；同一批货每天重复出现在清单里，跨班次交接靠表格和记忆。
5. **无人值守时段空窗**：夜班、周末、节假日无主动巡检，异常持续累积。

### 3.2 问题定位：只有结果行，没有证据链

1. **缺少上下文**：一条「未上架」记录背后是哪个通知单、哪个客户、哪个供应商、卡在哪个环节、已滞留多久，需要跨多个菜单手工拼接。
2. **跨栈口径不一致**：单据在 Java，储位与库存在 C++，效期在视图层，同一指标在不同入口可能给出不同结果，排障时先要花时间确认「以哪个为准」。
3. **缺少归因**：临期是入库时生产日期录错，还是先进先出未执行；异常出货是订单问题还是拣货问题；目前只能依赖老员工经验判断。
4. **缺少建议动作**：系统告诉你「有 6 条临期」，但不告诉你「先处理哪 2 条、移到哪个储位、通知哪个岗位」。

### 3.3 风险前置：只有阈值结果，没有趋势与闭环

1. **只能看「已经发生」**：现有视图已具备剩余天数、过期比例等字段，但没有被用于「未来 N 天将新增多少临期」的前置判断。
2. **规则不可配置**：预警阈值固化在查询与视图中，业务调整阈值需要研发介入。
3. **无责任路由**：告警不携带责任岗位，只能靠群里喊人。
4. **无时效与升级机制**：告警发出后没有认领、处理、关闭、超时升级的约束。
5. **无闭环度量与审计**：处理率、平均处理时长、重复发生率没有沉淀；「谁在何时收到、依据什么处理」无法回放。

### 3.4 工程侧待解决问题

巡检所需的「异常出货」「温度读取」「通知发送」尚未封装为 Agent 工具；告警状态、去重键、推送记录缺少存储载体；巡检的调度触发与幂等机制尚未建立。

## 四、核心目标与价值

### 4.1 核心目标

1. **从「人找异常」转为「异常找人」**：巡检按班次自动执行，结果主动送达责任人，不再依赖人工打开页面与导出 Excel。
2. **每条告警自带证据链**：异常对象、来源单据、关键字段、命中规则、发现时间、traceId 一次给全，排障不再跨菜单拼接。
3. **建立告警生命周期**：待处理 → 处理中 → 已关闭 / 已忽略（需填原因），跨班次可交接，超时未认领可升级。
4. **风险前置**：从「已过期」前移到「临期、超时前」，按剩余天数或剩余时长排序，给出优先级而非平铺列表。
5. **可配置、可降级**：巡检频率、阈值、责任岗位、通知渠道可配置；模型不可用时降级为规则模板巡检，保证不漏报。
6. **只读安全边界**：v0.2 不执行任何写操作，建议动作由人确认后在原业务页面执行。

### 4.2 核心业务维度

| 维度 | 设计要求 |
|---|---|
| **触发条件** | ① 定时：班前、班中、班后三类时点，频率 `[TBD]`；② 手动：主管随时发起一次巡检；③ 事件（P1，可选）：验收完成、上架完成、出库确认后触发增量巡检；④ 补偿：失败或漏跑后可重跑，按「规则 + 对象 + 时间窗」幂等去重 |
| **覆盖范围** | 效期、收货未上架、进货延时、出货异常、温度、待办积压六类；按仓库、客户、货主、责任岗位过滤；首版覆盖范围 `[Assumption, TBD]`（建议先单仓） |
| **处理时效** | 分三级：P0 即时推送、P1 班中汇总、P2 日报；发现时延、推送时延、认领时延、关闭时延、升级时延分别定义，具体数值 `[TBD]`；巡检单次执行端到端时长 `[TBD]` |
| **输出形态** | 分级告警清单 + 证据链 + 建议动作 + 责任岗位 + traceId；不输出 Excel 文件 |
| **边界** | 只读；不修改温度等主数据；不执行上架、转移、过账；不替代原有页面，只做发现与提醒 |

### 4.3 价值

- **业务价值**：临期与过期处置提前，减少报废；未上架滞留缩短，释放库容与月台；异常出货早发现，降低错发漏发；补齐夜班与周末的巡检空窗。
- **管理价值**：告警处理率、平均处理时长、重复发生率可度量，交接班有据可查，责任可追溯。
- **技术价值**：沉淀调度触发、幂等去重、告警状态机、通知通道、实体解析五项公共能力，为后续收货上架、波次优化等写操作场景铺路。
- **体验价值**：把「四个页面 + 多次导出 + 群里喊人」压缩为「一张分级清单 + 一次认领」。

## 4.4 判定规则与运行参数

### 4.4.1 判定字段与分级规则

判定字段均已核对现有实体与视图，不是假设：

| 异常 | 判定字段（已核实） | P0 | P1 | P2 | 默认值依据 |
|---|---|---|---|---|---|
| 效期 | `mv_stock_yj.res_date`（剩余天数）、`dqr`（到期日）、`guoqibili = res_date / bzhi_qi`（剩余保质期比例） | `res_date < 0`（已过期） | `0 ≤ res_date ≤ 7`，或 `guoqibili ≤ 1/3` | `7 < res_date ≤ 30` | 7 天是可执行出库窗口；30 天对齐月度补货/盘点周期；比例规则解决长短保质期差异，取“天数/比例”中较严者 |
| 收货未上架 | `wm_in_qm_i.create_date`（收货日期） | 滞留 > 8 小时 | 4–8 小时 | 2–4 小时 | 8 小时等于一个班次；2 小时等于一个上架波次；2 小时内属正常作业节拍，不告警 |
| 进货延时 | `im_data`（约定到货时间），沿用现有 `im_data < now` 口径 | 延时 > 24 小时 | 延时 2–24 小时 | 延时 0–2 小时 | 不改变“是否延时”的定义，只做分级，保证与现有页面口径一致 |
| 出货异常 | `wm_to_down_goods.create_date`（下架日期）+ 闭环状态 | 超过 1 个工作日未闭环 | 当日新增 | — | 直接影响发货，按工作日而非自然日计算 |
| 温度 | `wm_wendu.wendu_zhi`（温度值）、`wendu_cjsj`（采集时间），区间来自温度属性 | 超限 ≥ 2℃ 或持续 ≥ 30 分钟 | 超限 < 2℃ 且 < 30 分钟 | 超过 2 个采集周期无新数据 | 温度“没数据”比“数据异常”更危险，必须单独成级 |
| 待办积压 | 系统首页待办计数（待收货/待上架/待拣货） | — | 连续 3 个巡检周期增长 ≥ 30% | 单周期增长 ≥ 30% | 仓库规模差异大，用变化率而非绝对件数，避免小仓误报、大仓漏报 |

分级统一含义：**P0 = 已造成或即将造成实质损失；P1 = 需当班处理；P2 = 需关注并纳入计划。**

### 4.4.2 责任归属：系统角色与业务岗位分离

- **系统角色**（管理员、普通管理员、财务、客户、仓库经理、仓库管理）只决定**数据可见范围**，沿用现有 RBAC 与数据权限，不用于决定告警推给谁。
- **业务岗位**决定**告警归属**，通过“异常类型 × 仓库 → 岗位/人员”的配置表维护，首版用配置文件，后续补配置页面。

| 异常 | 首责岗位 | 协同 | 升级对象 |
|---|---|---|---|
| 效期 | 质检/效期专员 | 仓库经理、客服 | 仓库经理 |
| 收货未上架 | 上架组 | 收货组 | 值班主管 |
| 进货延时 | 收货组 | 客服（对外通知） | 仓库经理 |
| 出货异常 | 单证/客服 | 出库组 | 值班主管 |
| 温度 | 库管/设备 | 质检 | 仓库经理 |
| 待办积压 | 值班主管 | 各组组长 | 仓库经理 |

### 4.4.3 通知渠道优先级

现有可用通道只有站内公告、站内消息、短信、邮件，按“打扰成本 × 时效要求”分配：

| 级别 | 工作时间 | 非工作时间 | 未认领升级 |
|---|---|---|---|
| P0 | 站内消息 + 短信 | 短信 + 站内消息 | 30 分钟未认领 → 上级短信 |
| P1 | 站内消息 + 班中汇总 | 次日班前汇总 | 当班未认领 → 值班主管 |
| P2 | 日报/公告 | 日报 | 无 |

- **邮件**只用于日报/周报汇总，不发送单条告警。
- **公告**只用于全仓广播（如温度异常影响多个客户），不承担个人责任闭环。
- **短信**只给 P0 与升级，控制成本与打扰。

### 4.4.4 记录保留周期

| 数据 | 在线保留 | 归档 | 依据 |
|---|---|---|---|
| 告警记录（`agent_alerts`） | 180 天 | 1 年 | 与月度对账、季度盘点、年度审计节奏对齐，是业务凭证 |
| trace / 工具调用（`agent_traces`、`agent_tool_calls`） | 90 天 | 不归档 | 技术凭证，巡检数据量大 |
| 日/周聚合统计 | 2 年 | 长期 | 管理度量与趋势分析，数据量小 |
| 通知发送记录 | 90 天 | 不归档 | 排障与投诉举证 |

### 4.4.5 仍需业务一次性确认的三个参数

这三项不是“需求未知”，而是上线前确认即可，不阻塞开发：

1. **温度采集频率**：决定“数据缺失”的判定窗口，默认按 1 小时计。
2. **首版是否多仓/多货主**：建议首版单仓，配置层预留多仓维度。
3. **客户合同或合规对告警记录保留期的特殊要求**：若无特殊要求，按 4.4.4 执行。

以上阈值全部**配置化**（配置文件或配置表），不写死在代码里；首版采用上述默认值，上线两周后依据误报率与漏报情况校准，不需要在需求评审阶段继续等待。
